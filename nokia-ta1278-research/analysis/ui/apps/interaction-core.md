# 可复用的交互内核

本轮继续对本机 `17.00.17.02` 的系统代码逐分支核对。可运行规则在 `tools/native_app_rules.py`，地址、结构字段、范围 SHA 和局限在 [interaction-core-rules.json](interaction-core-rules.json)。没有执行固件。公开框架只用于命名；下列数值和条件均回查本机字节。

## 短信屏幕计数

`88351b12` 计算页数，`88352296` 计算本页剩余数，`88352232` 用 `user+352308` 的 `%d/%d` 格式化为“剩余/页数”。`88351bdc` 是控件显示接口；正文菜单 `883989d4` 也调用获取剩余数的接口。不能把彩信 `883965f0` 的 `%ld/%ld` 页码/大小显示当作短信计数。

`886240c8` 初始化短信控件：UCS2 的 140/134 字节容量明确右移一位，得到 70/67。普通默认字母表是 160/153；两组语言扩展容量是 155/149、155/146。编码设置 1/2 会改变 default 槽的容量，设备当前设置没有读取。

当需要 UCS2 时，used 是 UTF-16 单元数；否则是 `uint16(str_len + default_ext + r8_two)`。used 不超过 single 时，页数 1、剩余 single-used。超过时，页数为 `(used-1)//multi+1`，剩余为 `(multi-used%multi)%multi`。原生还保留 multi=0 分支和 u16 回绕，规则实现没有擅自修正。

**屏幕计数与发送打包必须分开。** 例如 152 个 A、一个 €、152 个 A，默认字母表共 306 单位，屏幕显示 `0/2`；发送器另行避免把 ESC 留在段末。旧参考模型按发送切段求 UI 页数，已经修正。

还有一处真实分支差异：r8_two 非零时，剩余函数使用 r8_two 容量；页数函数还检查语言计数 +250/+254/+256，可能改用 r8_one 容量。这不代表常见文本必然触发，但复刻底层规则不能把两个函数强行合成一个。

`880b0f0e` 是插入/删除后的计数更新入口，调用 `883a492c` 分类字符、`883a4ade` 分类语言，再增加或减去控件字段。后者在本机只更新语言槽 0/2/4，槽 1/3 为零。5 个常量判断的全部 65,536 种 UTF-16 输入均经受限比较树核对，没有执行固件。

两张 128 项表在 `user+c1797c / c17a7c`；217 项转换对在 `c172ec`。已导出到 [字符表](sms-character-tables.json)，含偏移、哈希和转换目标。SMS 判定优先级为 UCS2 → R8 双字节 → R8 单字节 → 默认扩展；默认扩展还受 sms_encode=2 抑制。alphabet_management=0 时，转换表成员会清 UCS2 分类，但这不等于已经在编辑框替换文字。

原生特殊行为保留：FF 不在默认扩展判断中；ESC 属于 R8 双字节集合；每个 UTF-16 单元独立分类，代理项不会合成 Unicode 码点。`Ş` 本身可留在 GSM 路径，混入 `ª` 则语言组合判断要求 UCS2。

当前 `sms_counter()` 已使用本机分类和计数公式；只将 alphabet_management=1、sms_encode=0 及普通页容量作为明确的复刻配置。实际设备设置、运行时配置切换、完整发送转换、T9 和自动 MMS 转换仍需单独处理。

## 浏览器字段

WML/XHTML 输入窗口共用窗口 ID `60015` 和控件 `60065`。handler 分别为 `88b4896e`、`88b48a76`。e001/e004/fa16/fa1b 确认，e002/fa17 取消，f022 清理窗口上下文。

字段格式解析 `88b488b4`：默认最多 1024 UTF-16 单元；数字累计长度，`*` 设为 1024，最终 0 或超过 1024 归为 1024。A/a、N、n/X/x、M/m 选择不同数值输入掩码，未知字符选择 63/4。不能把它当正则表达式。XHTML 格式 getter `88629bc2` 固定返回 0；正的 maxlength 属性覆盖格式长度并限制到 1024。密码字段 edit_type=4，普通=1；无格式指针的密码字段使用 56/16 掩码。输入掩码的完整输入法名称未强行命名。

创建编辑器时只复制 `min(原值长度, limit)`。WML 确认检查上下文/布局，读取编辑框、更新值并关闭。XHTML 还检查对象 +8f/+90 两个字节；非零时关闭但不写值。可写时先比较旧值，更新后若改变则请求事件 7 回调。取消只关闭，不走 setter。两个 guard 的语义和完整 JavaScript 回调仍未恢复。

参考 BrowserApp 已接入长度、guard 和 change effect。过长的外部测试输入会报错并留在编辑页（P 适配器防护）；真正 UI 应在编辑阶段限制输入。选择列表也已接入下述原生提交规则；完整 DOM、JS 和提交仍由适配器负责。

## 选择框、复选框和表单

WML `88b48350`、XHTML `88b487c4` 共用列表控件 `60064`。同样的确认事件，在单选和多选中含义不同：

| 操作 | 单选 | 多选 |
|---|---|---|
| 确认 e001/e004/fa16/fa1b | 提交列表选择，关闭 | 保持窗口，交给列表控件切换勾选 |
| 返回 e002/fa17 | 关闭，不提交 | 提交列表选择，关闭 |
| 上下文或布局失效 | 关闭，不提交 | 关闭，不提交 |

XHTML 单选确认后，选中标记有变化才请求事件 7；多选返回提交分支没有这次请求。不能把输入框的“取消不保存”规则套到多选框。

`88b48534` 逐项将列表勾选写到 option+5a，单选时写 select+70 索引，最后调用刷新函数。若外部给出多个勾选，最后一个索引覆盖前面的值；规则没有擅自规范化输入。WML 写 option+4，之后的 WML task/value 副作用仍委托给适配器。

`880bed86` 的输入动作表有 10 项，原字节和目标见 JSON。checkbox 在 click 回调之前改变 checked，回调拒绝后本函数不会回滚；不能照搬桌面浏览器的预期来修正它。radio 清除同组候选再选当前项，但原生字符串比较及完整 DOM 生命周期仍需追踪。

提交 type4 先走 form+130 回调，再沿链表检查文本/密码项。某些非输入或其他类型分支直接进入提交出口，并非“检查所有字段”的抽象流程。type7 用不同标志直接提交。校验失败进入 `88b46656`；具体格式验证及 `88b5562a` 的请求编码未恢复完整。

重置 type5 通过 form+134 回调后调用 `880bea84`：文本/密码恢复默认字符串，checkbox/radio 恢复默认勾选，选择框恢复每项默认标志及索引。选择框另有 `非多选 && size<=1 && index==0` 的首项回退；这里检查的是数值零，不能改写成“没有任何项选中”。内存不足、空 DOM 项和 JavaScript 的副作用不在纯规则内。

## 短信发送与存储确认

`883c3986` 是发送成功处理。若需要保存且 save_storage 为零，只写 `send_status=1` 等存储确认，不进入下一段或下一个收件人。若存储确认已到，则更新索引记录、清 save_storage/send_result，再继续发送。当前段有后续时优先发送下一段，段号按 u8 加一；没有后续才清理成功收件人并移动到下一收件人。移动失败或发送入口返回 4 时结束本次操作。

`883c435e` 是收到存储确认后的继续处理，不能当作整个原始存储回调：

| 待处理状态 | 原生后续 |
|---|---|
| 1 | 清存储标志；发送下一段，否则转下一收件人 |
| 3 / 4 | 清存储标志；跳过余段，转下一收件人 |
| 5 | 有余段时设 operation=12 并保存下一段；没有余段则转下一收件人 |
| 其他 | 不继续发送 |

各正常出口清 `send_status=0`。状态 5 的保存错误 8 打开空间不足提示及继续回调；其他非零错误提示 Error 并关闭发送窗口。**保存失败长短信的余段与重试发送是不同路径。** 字段名由固定版本公共源码关联，数值、调用和写入顺序均核对本机指令。真实存储、所有信箱索引和基带异常仍未完整建模；合成 SmsApp 的高级流程仍有 P 策略。

## 浏览器加载阶段

页面文档完成时，`88b65986` 设置子资源总数，清已收计数和当前请求句柄；子资源为零才立即转停止状态。每个子资源完成后，原生进度参数为 `(current+total, 2*total)`，到达 total 时结束。它不是下载字节百分比。page-stopped 消息遇请求状态 1/2/3 会保留新的加载状态；不能无条件把后来的请求清掉。

## 音乐返回

`88acf6f6` 先调用 `8861999c(0)`；主播放状态非零、review-open 为真且 review state 为 0/1，才依次执行 `601092(0) → 3f25fc → 3f2646 → 601092(1)`。review 名称有原生日志支持，但两个 helper 的所有媒体副作用尚未恢复。

接着按 `ab8438` 返回的上下文标志分流：真则关闭当前窗口；假则关闭存在的 `e0017`，再打开描述 `8820311c`。因此“返回始终继续播放”仍是新程序策略，不能当作恢复结论。`music_back_plan()` 提供数值条件和有序 effect，供适配器逐步替换。

## 音乐队列与播放结束

`8868629c` 将重复/随机设置转换成手动队列模式；`886862d4` 给播放结束使用。下表每格为“随机关闭 / 开启”：

| 重复设置 | 手动模式 | 播放结束模式 |
|---|---|---|
| Off (0) | 4 / 1 | 4 / 1 |
| All (1) | 3 / 2 | 3 / 2 |
| One (2) | 3 / 0 | 0 / 0 |

`88600066` 有原生日志 `MMIAPIMP3_PlayMp3CallBack`。只处理主状态 2/3；review 标志非零会跳过正常队列推进。模式 0 不移动队列，符合重复当前曲目的分支结构；模式 1–4 调用 `8861b452(0)` 推进。推进失败调用停止相关 helper，推进成功再通知 UI，并仅在主状态 2 进入播放 helper。此处存在同步回调后的再次查询，纯规则使用稳定快照，尚未证明重入行为。

`88600036` 检查不支持曲目的数量（日志 `GetNoSupportNumber`）：队列非空且模式 2/3 的失败数达到曲目数，或模式 0 已有失败，才触发该终止保护。模式 1/4 的队尾主要由推进函数返回值判断。`88619b68` 的索引算术本身会取模环绕；`8861b452` 对存储模式 1/4 的回到零另行判失败。手动切歌入口及边界检查与自然结束不同。

已恢复这些数值分支、通知顺序及有序 helper 调用；随机排列生成、文件系统曲库更新、review 的全部副作用和真实音频设备尚未闭合。高级 MusicApp 的队列策略仍须保留 P 标记。

## 开发边界

上述结果可供后续本地程序复用；用户要求先继续逆向，当前尚未初始化应用。电话/短信后端、浏览器完整 DOM/JS/TLS、原机音频服务、T9 排序、像素级布局、所有系统应用异常状态并没有恢复。新程序必须区分本机证据、简化服务和设计选择；不能称为原固件模拟执行。已确认的实现约束见 [后续程序计划](replica-plan.md)。
