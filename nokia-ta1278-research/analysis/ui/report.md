> 此为早期调查快照。字体主体及多数剩余图像已经在后续解码，当前结果见 [资源与交互恢复报告](recovery-report.md)。

2026-10-25；仅分析本机双读一致的系统工作副本，没有操作 USB、读取私人短信或执行固件代码。软件版本依据 kernel 中的 `17.00.17.02`。

本轮已经取得可直接用于复刻研究的图像、三语言文字、菜单注册表、输入字符表和代码定位。**字体原件已提取，字形主体尚未解码；当前成果不等于完整还原字体渲染或实机交互。**

## 数据来源与地址约定

输入路径：`analysis/work/system-20261025T054301+0800/`。

- `user.bin`：13,312,500 bytes，SHA-256 `8f0db2dc82f9e763cb700c2e5781b7ca7125a4d250f4c075dbec793eb549c1ca`。
- `mmi.bin`：11,835,196 bytes，SHA-256 `14c573027f375ea6b5f8ead2c6c432f2773f373faaa3c8a33261d0de9737886c`。

下面代码地址按 `0x88000000 + user.bin 文件偏移` 表示，**包含 DHTB 头**；函数指针最低位为 Thumb 标志。多个表指针、字符串引用和调用目标相互吻合，但这不是现场读取的 PC 寄存器。`user.analysis-only.elf` 是给 LLVM 的人工分析容器，不能启动或刷入手机。反汇编片段可能夹带文字和常量池；只将已人工核对的指令范围作为行为证据。

## 字体及文字资源

字体区位于 MMI `0x35cbec`，3 个字体 ID 各有三个语言槽，槽指向相同的字体数据，不能计为九套独立字体。

| ID / 标记 | MMI 偏移 | 字节数 | 非零字符映射数 | 主体相对偏移 |
|---|---|---:|---:|---|
| 0 / latn | `0x35cc4c` | 90,983 | 1,313 | `0x81c` |
| 1 / hani | `0x372fb4` | 2,144,201 | 7,479 | `0x8a74` |
| 2 / hani | `0x57e780` | 4,713,777 | 13,497 | `0xd064` |

三份文件均以 `sfon` 开头，头部为大端字段；`+0x2c` 包含类似 OpenType cmap 的 platform 3 / encoding 1 / format 4 表。映射并集覆盖 17,564 个码位。**映射项数不是字形总数**，映射中的 glyph ID 并不稠密，尚未与不透明的字形主体逐项核验。

已经对照固件函数，而非仅套用标准库：

- `0x88563970` 初始化 cmap，构造分段数组指针与字符区块缓存。
- `0x88563ab6` 查找字符，先把 U+00A0 转换为 U+0020，并使用低八位索引的缓存。
- `0x88563b72–0x88563b86` 的 range-offset 分支直接返回 glyph 数组值；没有再加 idDelta。
- `0x88563ba6–0x88563bb8` 的无 range-offset 分支返回 `(codepoint + delta) & 0xffff`。
- 三份表声明的 format-4 长度均比最后一个被引用 glyph word 少 2 字节；解析器同时以实际字体主体边界限制读取，并显式记录这一格式差异。

导出的 cmap 是资源映射，不包含查找函数所有过滤、脚本整形、fallback 和缓存行为。镜像中有 `spml_font_map.c`、`spml_bidi.c`、`spml_otf_gsub.c`、`spml_otf_gpos.c`、`spml_autofit.c` 等模块线索，说明文字系统包含比逐字符贴图更多的处理路径；不能由文件名推定本机启用了所有脚本功能。

目前没有还原 SFON 字形主体、字宽、基线、字号和抗锯齿参数，没有生成伪 TTF。资源浏览器以电脑系统字体显示文字，不能用于判定手机字形。原始 SFON 与 SHA-256 已独立保存，后续可沿上述字体对象和 glyph lookup 的调用链继续研究。

字符串块中有三个语言描述项，每项指向 `count` 个 u32 偏移；偏移相对 TRES 资源组。普通字符串零结尾；`80 00 + u16LE 字节长度` 后面是定长 UTF-16LE。解析得到：

- 17,197 条纯 ASCII；5,226 条严格 UTF-16LE，均解码成功。
- 77 条非 ASCII 的单字节字符串保留原始十六进制，暂以 Latin-1 无损展示；代码页未确认，见 [decode-errors.json](decode-errors.json)。不能把它们称作已准确译码。
- 槽 0/1/2 的英文、简中、繁中名称根据文本观察命名；不是已解码的正式 locale ID。部分槽仍含英语、其他语言和未使用的通用模板。

## 菜单注册、素材与应用入口

`user.bin + 0x21cf2c` 是 30 × 24-byte 的编译期注册表。`0x8816cfb0` 加载数量 30，`0x8816d0ba–0x8816d128` 按 24-byte 步长查找应用 ID，并拷贝资源和 handler 字段。

记录布局：`app_id, text_resource, icon_resource, secondary_resource, handler_thumb, parameter`。secondary_resource 的最终用途尚未确认。资源 ID 的低 16 位使用 **从 1 开始**的索引；资源组位于中间字节。本轮所有 30 项文字/图像对照吻合这一解码方式。

例如短信入口：

- 注册表偏移 `0x21cfa4`，app ID `1`。
- 文字 `0x40000a22` → group 0 / index 2593 → `Messaging / 信息 / 訊息`。
- 图像 `0x400001b5` → group 0 / index 436 → 76×76 绿色消息气泡图标。
- Thumb handler `0x880bcf0f`；代码 `0x880bcf0e` 跳转到 `0x8807fea0`。

注册表同时包含支付宝、喜马拉雅、地区运营商、社交和游戏条目，说明它不是本机当前可见菜单的简单列表。动态开关、排序、安装状态、地区配置和子菜单层级仍需进一步追踪。已确认入口与资源关联，可供复刻使用；未确认网格行列、焦点环绕、软键文字的动态切换和返回栈。

短信资源组 8 中的本地化标签已经提取，例如：

| 资源 ID | English | 简体中文 |
|---|---|---|
| `0x400800c0` | Insert options | 插入选项 |
| `0x400800c1` | Insert symbol | 插入符号 |
| `0x400800c2` | Insert smiley | 插入表情符号 |
| `0x400800c3` | Insert template | 插入模板 |
| `0x400800e9` | New message | 新建信息 |
| `0x40080114` | Character support | 支持不同字符 |

这些标签证明资源存在，不单独证明当前短信窗口一定开放相应操作。

## 按键、多击与预测输入

内核 `0xb401cc` 的 8×8 u16 矩阵有 19 个非空项，包含拨号键、左右软键、四方向、0–9、星号和井号。名字按已使用的上游枚举解释。**矩阵没有值 13/CENTER，也没有独立电源键项**；先前工具字典包含 CENTER 名称并不代表实机矩阵存在该项。确认键、返回键是否复用软键及独立扫描路径仍未知。

输入表不是物理按键扫描表。函数 `0x8802f1f8` / `0x8802f220` 从 `0xc35a08` / `0xc36640` 两个注册表按模式码取字符表，共 391 / 390 条记录，指向 147 份独立表。模式码到用户可选语言/输入模式的完整对应仍未知。

`0x8802f33c`、`0x8802f354` 确认字符表结构：12 条记录，每条 80 bytes，即 `u16 count + 39 × u16 code unit`。获取候选使用 1-based 序号；序号 0 所在位置是 count。两条记录的未使用填充区非零，解析器保留其存在，不把填充当字符。

以 `user + 0x21d592` 的一组小写拉丁表为例：

| 键 | 按表顺序的候选 |
|---|---|
| 1 | `.,'?!"1-()@/:_` |
| 2 | `abc2äæåàáâãç` |
| 3 | `def3èéêëð` |
| 4 | `ghi4ìíîï` |
| 5 | `jkl5£` |
| 6 | `mno6öøòóôõñ` |
| 7 | `pqrs7ß$` |
| 8 | `tuv8ùúûü` |
| 9 | `wxyz9ýþ` |
| 0 | 空格、`0`、LF (`U+000A`) |

`0x884816be–0x8848173e` 比较最近按键，读取候选数量，递增序号，超过数量后回到 1，再获取字符。上下文 `+0x38` 为最近候选键槽，`+0x3a` 为候选序号；提交函数 `0x88481588` 将键槽设为 12、序号清零。`0x88482d10` 向定时封装传入常数 750，定时 ID 为 5；**单位和实机触发时延尚未验证**。

固件还有 Smart9Key 路径和本地化 `Predictive text on/off` 标签，支持“存在预测输入实现和设置资源”的结论。未提取完整词库或证明 T9 品牌，不把多击字符表当成预测字典。

## 光标、退格与短信长度

通用编辑控件的指令共同支持以下字段解释（不是完整 C 结构体）：

| 对象偏移 | 代码证据支持的含义 |
|---|---|
| `+0x90` | 16-bit 文本单元缓冲指针 |
| `+0x94` | 文本长度字段（u16） |
| `+0xae` | 当前光标位置（u16） |
| `+0xc2/+0xc4` | 选区两个端点（u16） |
| `+0x240` | 覆盖文本范围的链表，节点含起点、长度和 next |

`0x882ffe3c` 对移动方向值 1–4 分发，其余值进入 `GUIEDIT_MoveCursor` 错误路径。`0x882ffd36` 处理选区端点、行信息和刷新通知；本轮未把四个值强行命名为上下左右。

`0x880951fa` 的删除路径先查询选择状态；无选区且光标为零时退出。在普通路径中选取 `cursor−1`；若 `cursor≥2` 且范围链表查询命中 `cursor−2`，则改用 `cursor−2`。随后经控件方法表 `+0xd4` 回调处理范围，最后更新内容。**这里的两单元分支不能直接解释为 UTF-16 代理对**：查询函数 `0x88095f98` 实际访问范围链表，没有检查 surrogate 码位。长按重复删除和短信窗口对该控件的绑定还未完整还原。

换行已有两处独立证据：上述键表含 LF；`0x88095ff6–0x88096004` 在 16-bit 文本缓冲中扫描值 10 作为行边界。具体按键组合、软键“插入”路径和输入模式限制仍需要继续追踪。

短信长度函数 `0x88b50d34` 有确定的分支输出：

- alphabet=0、特殊参数及两个全局开关均为零：single=160，split=153。
- alphabet=1 或 2、特殊参数为零：single=140，split=134。
- 另有 154/146、155/149、155/146、133/127、133/128 等条件分支；各开关业务含义未完全确认。
- 下游 `0x88b50ec4` 检查段末字节 `0x1b`，若命中则减少一个单元，避免将转义引导字留在段尾。

160/153 与 ESC 的组合支持 GSM 7-bit 解释；140/134 的两字节文本换算可得到 70/67，但本轮尚未把所有 alphabet 枚举和短信界面的字符计数、剩余数、分段提示串连成完整调用链。因此不能宣称已经实测“中文最多 70 字”或写死所有分段容量。

## 给复刻实现的约束

现在可以直接使用提取图标、三语言资源 ID、主菜单入口映射、物理矩阵和指定模式字符表。文本模型应区分缓冲文本、光标、选区、待确认多击字符、输入模式和传输编码；已发现的代码路径支持这些状态相互独立。

仍不能锁定的内容：手机字形/字宽/基线、实际菜单显示与顺序、状态栏和软键栏尺寸、方向事件与物理键完整映射、750 的单位、长按连发间隔、预测词库、短信计数的显示规则、返回/退出是否保存草稿。这些应保持待验证，不能以常见功能机习惯代替本机证据。

最值得继续的离线路径是：沿 `0x88563ab6` 的 glyph ID 追进 SFON 主体读取/栅格化；沿短信 app=1 的 `0x8807fea0` 追到窗口定义、按键分发和计数绘制；追踪菜单注册表的过滤与排序调用者。本轮资源及精确偏移可直接作为下一轮入口，无需重新读取手机。

## 复现

在项目根目录，使用已有 Python、Pillow 与 Xcode LLVM：

```sh
python3 tools/extract_ui_resources.py
python3 tools/decode_abm.py
python3 tools/analyze_ui_code.py
python3 tools/build_ui_catalog.py
python3 tools/validate_ui_outputs.py
```

脚本只读系统工作副本，输出到 analysis；原件保留在 firmware/original。完整输入/派生文件校验值在项目 SHA256SUMS。网页不依赖服务器、外部字体、CDN 或远程脚本。
